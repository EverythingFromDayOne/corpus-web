# Verify recipe — what `hermes verify` covers, and what it doesn't

This file is the project-side companion to the saved manifest at
`.hermes/environment.json` (gitignored, regenerated by `hermes verify
--save`). It exists so the verify surface is legible to a human reader and to
CI without having to mentally model which app is on which port.

## TL;DR

| Probe                       | Command                              | What it proves                                                                 | What it does NOT prove                                                                  |
| --------------------------- | ------------------------------------ | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| `hermes verify` (root)      | `hermes verify`                      | `apps/web` builds, typechecks, lints, tests, and starts on `:3000`             | The api starts, connects to Postgres, runs migrations, or that any `/healthz` returns 200 |
| `pnpm verify:api-runtime`   | `pnpm verify:api-runtime`            | `apps/api` builds, Postgres comes up, migrations run → revert → run, API starts on `:3001`, `/healthz/live` returns 200, `/healthz/ready` returns 200 with `database:up` | That `apps/web` is healthy — pair with `hermes verify` for that                          |

## Why two probes instead of one

`hermes verify` is single-port / single-recipe by design (one `start`, one
`port`, one `readinessPath`). `corpus-web` has two runtime apps:

- `apps/web` — Next.js, port 3000, readiness `/`
- `apps/api` — NestJS, port 3001, readiness `/healthz/live` (no DB touch) /
  `/healthz/ready` (with DB up)

The saved manifest at `.hermes/environment.json` records `start: "pnpm dev"`,
`port: 3000`, `readinessPath: "/"`. Running `hermes verify` against it proves
`apps/web` boots end to end. It does NOT start or probe `apps/api`. A green
`hermes verify --json` returns `readiness: null` for the api because no
`start` phase executed for it — see D53 in `docs/DEBT.md` for the original
writeup.

The fix in this commit does not modify `hermes verify` itself — that would be
an upstream CLI change. Instead, it adds an out-of-band probe at
`scripts/verify-api-runtime.mjs` that exercises the full api lifecycle:

1. **preflight** — docker reachable, `.env` present (cp from `.env.example` if
   missing — local dev only, gitignored)
2. **build** — `pnpm --filter @corpus/api build`
3. **postgres-up** — `docker compose up -d db` at repo root, poll `pg_isready`
4. **migration-roundtrip** — `migration:run` → `migration:revert` → `migration:run`
5. **api-start** — `node apps/api/dist/main.js` in the background
6. **healthz/live** — poll for HTTP 200 (no DB touch)
7. **healthz/ready** — poll for HTTP 200 with `database:up` in the body (DB-up probe)
8. **teardown** — kill the API, `docker compose stop db` (volume preserved)

Exits 0 on full green, 1 on any failure. Phase status is printed one per line
so the output is greppable in CI logs.

## Where the recipe lives

| Path                                | In git? | Source of truth for                                       |
| ----------------------------------- | ------- | --------------------------------------------------------- |
| `.hermes/environment.json` (root)   | No (gitignored at `.gitignore:34`) | `hermes verify` reads this on every run; `hermes verify --save` regenerates it |
| `apps/api/.hermes/environment.json` | No      | Would be the api's companion manifest, but the directory name is gitignored and Hermes treats `.hermes/` paths as protected agent-instruction files. Out of scope for this commit. |
| `docs/verify-recipe.md` (this file) | Yes     | Human-readable surface for what `hermes verify` + `pnpm verify:api-runtime` cover together |

If a future commit lifts the `.hermes/` gitignore and adds a CI-runnable
recipe for `apps/api`, the script and this file stay as the source of truth —
the script already implements the lifecycle the recipe would describe.

## CI integration

Neither `hermes verify` nor `pnpm verify:api-runtime` is wired into
`.github/workflows/ci.yml` today — `hermes verify` is an agent-side tool and
the api runtime probe needs Docker which the GitHub-hosted runner can run
without privileged mode. Wire-up is a separate decision (D19's "site CI gates
missing" is the closest prior art). For now: run both locally before
declaring a branch green on the api surface.
