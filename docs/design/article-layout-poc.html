The stale-answer tax

Caching converts a latency problem into a correctness problem, and the bill arrives later.

Baseline Next.js 16.3
Kind Concept
Wave 1
Difficulty Advanced

Monday

You add 'use cache' to the product page. TTFB drops from 840ms to 40ms. Lighthouse goes green. You merge it and go to lunch.

Thursday, support forwards a ticket: “The price on the listing says €39 but checkout charges €45.”

The listing was cached at build. The price changed Tuesday. Nothing errored, no alert fired, no log line was written — the page was doing exactly what you told it to. You didn't buy speed. You borrowed it, and the interest is paid in wrong answers.

Part 1Three phases of a cached response

Every cached page — whether it is a marketing shell or a per-tenant dashboard — passes through the same three phases. Their costs are not comparable, and only one of them is unbounded.

Phase 1 · Prerender

At build, Next executes the cached scope and writes HTML to .next/server/app. This costs build minutes, once. It is O(routes) and you can see it in the build output. Never a production cost.

Phase 2 · Shell flush

On request, the edge finds that artefact and flushes it. No database, no origin, no render. O(1) and bounded — this is the entire performance win, and it happens before any per-user work begins.

Phase 3 · Boundary resolve

Each <Suspense> hole then resolves against the origin. O(boundaries × origin latency), unbounded, and it scales with how much of the page you left uncached. This is where the cost actually lives.

The build output tells you which one you got

Every next build prints the render mode per route. Three symbols cover almost everything, and misreading them is how a route silently goes dynamic.

Reading the build output
Route (app) Size First Load JS ◐ /products/[id] 2.1 kB 108 kB
◐ (Partial Prerender) prerendered as static HTML with dynamic holes └ <Suspense> boundary: PriceWidget → resolved per request

What you almost always want. The shell is cached and shared; only the boundary hits the origin. Phase 3 fires once per reader, for one component — not the page.

Route (app) Size First Load JS ○ /about 1.4 kB 96 kB
○ (Static) prerendered as static content no dynamic holes — zero origin hits at request time

Correct for content that changes only on deploy. Dangerous for anything with a price, a stock level, or a personalised greeting — this is exactly the Thursday ticket.

Route (app) Size First Load JS ƒ /dashboard 3.8 kB 142 kB
ƒ (Dynamic) server-rendered on demand reason: used `cookies()` outside a Suspense boundary

Usually accidental. One cookies() read above the boundary drags the whole route dynamic, and phases 1 and 2 stop existing. The reason line is the thing to read — it names the exact call.

Quick check1 / 1
Which phase has a cost you cannot bound at build time?
C. Phases 1 and 2 are visible in the build output and constant per request. Phase 3 scales with boundary count and origin latency, neither of which the build knows.

So who decides which mode a route gets? Not you, directly. The compiler infers it from what your code touches — and it will silently choose dynamic the moment you read a request-scoped value in the wrong place.

Part 2When caching turns against you

The reflex — and why it's wrong

“The cache is stale, just lower cacheLife.” It sounds like tuning. It isn't.

Lowering the TTL narrows the staleness window; it never closes it. At cacheLife('minutes') you have simply agreed to serve wrong prices for up to sixty seconds instead of three days. If serving a wrong answer is unacceptable, no TTL is correct — the value belongs below a Suspense boundary, not in the shell. TTL tuning is how teams spend a quarter converting a correctness bug into a smaller, harder-to-reproduce correctness bug.

Two ingredients turn a cache from a win into an incident, and neither one raises an alarm.

Ingredient 1 · Facts that expire faster than the TTL

Prices, stock levels, feature flags, permissions. Anything a human can change in an admin panel changes on human time — seconds — while your cache thinks in deploys. The mismatch is silent by construction: a stale page is a correct render of an old fact, so nothing in your stack has anything to complain about.

Ingredient 2 · Cache keys that multiply

A cache entry is keyed by everything the cached scope reads. Add locale, currency, and an A/B variant, and one route becomes a few hundred entries. Hit rate collapses, memory climbs, and the cache now costs more than it saves — while still being stale.

Part 3What each cached surface actually costs

A tenant-dashboard route, cached per tenant and per locale. Eight hundred tenants, four locales: 3,200 entries. Each holds a rendered payload. Hit rate is poor because most tenants visit once a day, so most reads miss and render anyway — you pay origin cost and storage. The cache is now a tax with no benefit.

The rule

Cache what changes on deploy. Stream what changes on human time. Never cache what changes per request. If you cannot say which of the three a value is, you are not ready to cache it.

Interview question

“Why not cache everything, given caching makes things faster?” A complete answer names three costs:

  1. Every entry is keyed by what the scope reads — keys multiply and hit rate collapses
  2. Every cached fact becomes an invalidation obligation you own for the life of the system
  3. Staleness fails silently: nothing errors, nothing logs, and the page looks correct

Naming the third is what separates a candidate who has run a cache in production from one who has read about caching.

Quick check1 / 1
A cached scope reads tenant, locale, and an A/B variant. 800 tenants, 4 locales, 3 variants. How many entries?
C. Keys multiply, they do not add. This is why an innocuous third input is usually the one that breaks the cache economics.

The bigger picture

Across both caching articles: Next 16 inverted the default → nothing caches until you say so → a cached page is a shell plus holes → the shell is free and the holes are not → and every cached fact is a promise you now have to keep.

Remember Thursday's ticket at the top. You can now say exactly what happened: the price lived in the shell instead of below a boundary, so it was frozen at build and no mechanism existed to notice. Not a bug in Next. A design decision, made implicitly, by adding one directive without asking which of the three kinds of value it was wrapping.
